# Free-Flow 开发工作流

## 约束（始终遵守）

- 不破坏现有代码
- 优先复用已有 Service
- 不新增重复 DTO
- 不修改公共接口
- 保证单元测试通过
- 不要修改无关代码
- 不要重构整个模块

## 参考文档

开发前必须阅读：

- `docs/architecture.md` — 架构设计与模块关系
- `docs/coding-style.md` — 编码规范
- `docs/database.md` — 数据库设计

---

## Phase 1：分析

收到 `tasks/<task>/` 下的新任务时：

**读取：**

- `tasks/<task>/01-task.md` — 任务描述
- `tasks/<task>/02-context.md` — 上下文信息
- `tasks/<task>/03-acceptance.md` — 验收标准

**生成：**

`tasks/<task>/04-plan.md`，必须包含：

```markdown
# 修改计划

## 涉及模块
- [ ] 模块名 — 修改原因

## 新增文件
- 文件路径 — 用途

## 修改文件
- 文件路径 — 修改内容

## 风险分析
- 风险点及应对措施

## 测试方案
- 如何验证修改正确性
```

**暂停，等待用户确认后再进入 Phase 2。**

---

## Phase 2：开发

收到确认后，按 plan 实现代码。

开发过程中：

1. 遵循 `docs/coding-style.md` 中的编码规范
2. 新增枚举遵循统一模式（@AllArgsConstructor + STATUS_MAP）
3. Controller 使用标准 try-catch + HttpBody 模式
4. 参数校验使用 VerifyUtil
5. 数据库访问通过 repository-starter 的 Service 层
6. 每完成一个模块的修改后立即编译验证

---

## Phase 3：验收

开发完成后：

1. 运行编译：`mvn compile -q`
2. 运行测试：`mvn test`（如需要中间件环境则说明）
3. 集成测试：可选，如果需要集成测试，并且评估必须人工介入，则需要在`result.md`中明确说明

**生成：**

`tasks/<task>/05-result.md`，必须包含：

```markdown
# 验收报告

## 修改文件列表
- 文件路径 — 修改说明

## 新增文件列表
- 文件路径 — 用途说明

## 删除文件列表
- 文件路径 — 删除原因（如无则标注"无"）

## 测试结果
- 编译：通过/失败
- 单元测试：通过/失败/跳过（附原因）

## 验收项完成情况
- [x] 已完成项
- [ ] 未完成项 — 原因

## 备注
- 其他需要说明的事项
```

## 子任务机制（Sub-Task）

### 触发条件

在任意 Phase 完成后，若发现以下情况，应创建子任务：

- **Phase 1 完成后**：方案存在遗漏、技术选型需调整、发现新的依赖关系
- **Phase 2 完成后**：实现过程中发现 plan 有缺陷、需要补充额外修改、接口设计需调整
- **Phase 3 完成后**：验收发现 Bug、测试暴露逻辑问题、需要回归修复

### 子任务创建规范

在当前任务路径下创建子任务文件夹，命名格式：`sub-<序号>-<简短描述>`

```
tasks/<task>/
├── 01-task.md
├── 02-context.md
├── 03-acceptance.md
├── 04-plan.md
├── 05-result.md（如已完成验收）
└── sub-01-<描述>/
    ├── 01-task.md
    ├── 02-context.md
    ├── 03-acceptance.md
    └── 04-plan.md
```

### 子任务文件内容要求

**`01-task.md`** — 必须包含：

```markdown
# 子任务：<简短标题>

## 来源
- 父任务：tasks/<task>/
- 触发阶段：Phase X 完成后
- 触发原因：<具体描述为什么需要这个子任务>

## 任务描述
<具体要做什么>
```

**`02-context.md`** — 必须包含：

```markdown
# 上下文

## 父任务方案回顾
<引用父任务 04-plan.md 中相关部分>

## 当前代码现状
<基于已有代码，说明当前实现状态和需要调整的部分>

## 约束与依赖
<本子任务需要注意的约束条件>
```

**`03-acceptance.md`** — 验收标准，格式与主任务一致。

**`04-plan.md`** — 基于现有代码生成修改计划，格式与主任务 Phase 1 输出一致，但需额外包含：

```markdown
## 与父任务的关系
- 父任务 plan 中需要修正/补充的部分
- 本子任务对父任务已完成代码的影响范围
```

### 子任务执行流程

1. **创建子任务文件**：按上述规范生成 01~03 文件
2. **执行 Phase 1**：基于现有代码（而非从零开始）进行分析，生成 04-plan.md
3. **暂停确认**：等待用户确认子任务 plan
4. **执行 Phase 2**：按子任务 plan 进行开发
5. **执行 Phase 3**：验收子任务，生成 05-result.md
6. **回归父任务**：子任务完成后，回到父任务继续未完成的流程

### 注意事项

- 子任务可以嵌套（子任务中发现问题可再创建子子任务），但建议控制在 2 层以内
- 子任务的 plan 必须基于**当前已有代码**生成，而非假设从零开始
- 子任务完成后，应检查父任务的 05-result.md 是否需要更新
- 多个子任务按序号递增：`sub-01-xxx`、`sub-02-xxx`
- 子任务同样遵循所有约束和参考文档要求

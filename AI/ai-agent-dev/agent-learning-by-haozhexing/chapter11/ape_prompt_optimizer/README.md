# APE 迷你实验：自动生成 system prompt → 打分 → 选优

第 11 章「自我进化与持续学习」里理论偏多，这个实验用最小代码把
**自我进化闭环的骨架**跑通一遍：让 LLM 自己写候选 prompt，再用留出集选出最好的那个。

## 一、它对应 APE 的什么

APE（Automatic Prompt Engineer, ICLR 2023）的核心思想只有一句话：

> 把 prompt 当成可以被搜索的参数 —— 让 LLM 生成一批候选，用数据打分，留最优的。

本实验的闭环：

```
Generator（LLM 生成 N 个候选 system prompt）
        ↓
Evaluator（在 14 条留出样本上跑分，指标 = 标签精确匹配）
        ↓
Selector（排序，保留 Top-1，写入 best_prompt.txt）
```

对应的正是自我进化系统里的 `Generator → Evaluator → Selector`。
**Reflector / Rewriter 不在本实验范围内**（那是 TextGrad、DSPy 的梯度式进化，等跑通这一步再加）。

## 二、为什么用「意图分类」这个任务

| 考量 | 说明 |
|---|---|
| 打分要确定性 | 输出是 6 个固定标签，用精确匹配即可，**不用 LLM-as-judge**，评分可复现 |
| 跑得完 | 8 候选 × 14 样本 ≈ 130 次调用，qwen3.7-flash 一分钟左右跑完 |
| 有区分度 | 混入边界样本（如「过了保修期维修要多少钱」像咨询又像售后），能拉开候选差距 |

数据集分两部分，这是**刻意的防作弊设计**：

- `DEMO_SAMPLES`（6 条）：给 Generator 看，让它知道输入输出长什么样
- `EVAL_SAMPLES`（14 条）：**绝不**给 Generator 看，只用于打分

如果混在一起，生成的 prompt 会直接把评测题背下来，分数就失真了。

还有一个对称的设计：**标签清单不写进候选 prompt，而是在运行时附在用户消息里**
（`ape.py` 的 `classify()`）。原因见「坑 1」—— 否则模型会自创标签，
导致大量输出无法解析，分数量的是脚手架而不是 prompt。

## 三、运行

```bash
cd AI/ai-agent-dev/agent-learning-by-haozhexing/chapter11/ape_prompt_optimizer

export QWEN_API_KEY=sk-xxxxxx
pip install -r requirements.txt

python ape.py --candidates 8
```

可选参数：

| 参数 | 默认 | 说明 |
|---|---|---|
| `--candidates` | 8 | 生成候选 prompt 的数量 |
| `--workers` | 8 | 打分时的并发线程数 |
| `--limit` | 0 | 只用前 N 条评测样本（0 = 全部），快速冒烟用 |
| `--temperature` | 1.0 | Generator 采样温度；想要候选有差异就别调太低 |

输出文件在 `output/`：

- `best_prompt.txt` —— 胜出的 system prompt
- `results.json` —— 所有候选的分数
- `traces.jsonl` —— 每次调用的完整记录（输入/输出/是否正确/耗时）

## 四、实测结果（qwen3.7-flash，8 候选 × 14 样本）

```
排名   候选         准确率        正确       解析失败
──────────────────────────────────────────────
1    #6          100.0%   14/14     0
2    #8          100.0%   14/14     0
3    baseline     92.9%   13/14     0
4    #2           92.9%   13/14     0
5    #7           92.9%   13/14     0
6    #1           85.7%   12/14     0
7    #4           85.7%   12/14     0
8    #3           85.7%   12/14     0
9    #5           78.6%   11/14     0
```

结论：**92.9% → 100%，+7.1 个百分点**。14 条样本上一个档位就是 1 条，
这个幅度说明不了太多，但足以看清机制：候选之间确实存在真实差距，且 Top-1 优于人工 baseline。

## 五、看结果时重点看三件事

1. **候选之间的分差**：如果全部 100 分，说明评测集太简单，该加难样本了。
2. **最优 prompt 相对 baseline 的提升**：如果提升为 0 甚至为负，说明这个任务
   的 prompt 已经饱和 —— 再怎么自动搜索也没用，得换优化对象（比如改工作流、加工具）。
3. **失败样本**：实验结束会打印最优 prompt 仍答错的样本，
   这些就是下一步 **Reflector（分析失败原因）→ Rewriter（定向改写）** 的原料。

## 六、调试时真实踩到的两个坑（比代码本身更有价值）

### 坑 1：候选 prompt 自创标签，导致大面积"解析失败"

第一版实现里，类别清单只在 Generator 的上下文里出现，没有约束它写进 prompt。
结果生成的 prompt 一字不提标签表，模型就自由发挥了：

```
期望: 退款申请   实际: 退货退款
期望: 物流查询   实际: 催发货
期望: 产品咨询   实际: 商品咨询
```

一排候选 7.1% ~ 28.6%，`解析失败` 高达 13/14。

**修法**：把标签表移到【用户消息】里运行时注入，候选 prompt 只负责角色、判别规则、
思考方式与输出格式。这不只是修 bug，更是原则：
**标签空间属于"任务"，不属于"prompt"**。所有候选必须面对同一份任务描述，
否则比拼的就不再是 prompt 好坏，而是谁自己列的标签更好认。

### 坑 2：`max_tokens` 卡太死，把 CoT 类 prompt 的答案截断了

有个候选要求"先列出关键证据点，再作最终裁决"。我把 `max_tokens` 设成 64，
输出在推理中途被砍掉，最终标签根本没生成 —— 评分把它当成"答错"。

这是**评测脚手架的问题，不是 prompt 质量的问题**。这类误判最危险，
因为它会让优化方向整体跑偏。修法：把输出预算放大（`max_tokens=512`），
并且抽取标签时取**最后一次**出现的合法标签
（CoT 输出里推理阶段会提到别的标签，例如"排除物流查询"，最终结论一定在末尾）。

> 顺带一个通用教训：**优化器和它依赖的脚手架是耦合的**。
> 脚手架有偏差，优化出来的"最优 prompt"就是过拟合到那个偏差上的产物。
> 这也是为什么第 18 章的评估体系要排在自我进化之前学。

## 七、还有两个容易踩的坑

- **评分抖动**：评估阶段用了 `temperature=0`。打分函数本身不稳定，进化就变成随机游走。
- **只跑一轮就下结论**：单次结果受采样影响很大。想认真对比，
  应把同一批候选跑 2-3 次取平均分（这就是第 18 章要讲的可观测性与评估体系）。

## 八、下一步可以怎么扩展（按性价比排序）

1. **加 Reflector + Rewriter**：拿 `traces.jsonl` 里的失败案例喂给 LLM，
   让它分析"这个 prompt 为什么错"，再定向改写 —— 闭环就完整了（TextGrad 的思路）。
2. **多轮迭代**：把 Top-1 当作种子，让它"基于这个 prompt 生成 5 个改进版"，
   迭代 3 轮，看准确率是否单调上升。
3. **换更难的评测集**：意图分类毕竟输出空间小。换成"客服回复质量"这类开放式任务，
   就必须引入 LLM-as-judge，届时会深刻体会到**评分器本身才是自我进化的瓶颈**。
